# برداشت فعلی از قالب نمونه، قالب وردپرس و پلاگین Webtanan Booking

این سند برای هم‌سو کردن برداشت فنی و محصولی نوشته شده است. هدف آن اجرای تغییر جدید نیست؛ هدف این است که دقیقاً مشخص شود من از پروژه چه فهمیده‌ام، کجاها اشتباه برداشت کرده‌ام، و قبل از ادامه توسعه چه تصمیم‌هایی باید از طرف شما تایید یا اصلاح شود.

## 1. وضعیت کلی پروژه

پروژه فعلی از دو بخش اصلی تشکیل شده است:

1. پلاگین `webtanan-booking`
2. قالب همراه `webtanan-saas-theme`

همچنین یک قالب نمونه HTML در مسیر زیر وجود دارد که باید منبع اصلی طراحی UI باشد:

`C:\xampp\htdocs\nobat\sample theme\`

فایل‌های نمونه:

- `index.html`
- `dr-list.html`
- `dr-profile.html`
- `dr-dashboard.html`
- `patent-dashboard.html`

برداشت درست این است که خروجی نهایی باید از نظر تجربه کاربری، چیدمان، منوها، sidebar، کارت‌ها، فاصله‌ها، رنگ‌ها و رفتار موبایل به این فایل‌ها وفادار باشد. در عین حال داده‌ها باید واقعی و پویا باشند و از پلاگین/REST/دیتابیس بیایند.

## 2. اشتباه برداشت قبلی من

اشتباه اصلی این بود که من به جای اینکه sample HTML را «منبع حقیقت» بگیرم، چند لایه CSS و کلاس جدید روی خروجی موجود اضافه کردم. نتیجه این شد که:

- هر بخش یک زبان طراحی جدا پیدا کرد.
- قالب و پلاگین هر کدام جداگانه تلاش کردند UI بسازند.
- sidebarها دقیقاً مطابق نمونه و نقش کاربر پویا نشدند.
- کلاس‌های sample فقط به بخشی از DOM چسبانده شدند، نه اینکه کل ساختار صفحه طبق sample بازسازی شود.
- جریان رزرو نباید قربانی تغییر UI می‌شد، اما احتمالاً اتصال eventها، دکمه‌ها یا DOM رزرو با تغییر ظاهر ناپایدار شده است.

برداشت اصلاح‌شده:

ظاهر نهایی نباید ترکیبی از چند نسل UI باشد. باید یک سیستم واحد وجود داشته باشد که sample HTML اساس آن است و پلاگین فقط داده و رفتار پویا را داخل همان ساختار قرار می‌دهد.

## 3. نقش درست قالب

قالب `webtanan-saas-theme` نباید فقط یک پوسته تزئینی باشد. طبق برداشت فعلی، قالب باید shell عمومی سایت را کنترل کند:

- هدر سایت
- فوتر سایت
- ساختار صفحه اصلی
- ستون کناری عمومی سایت، در صفحاتی که نمونه sidebar دارد
- رفتار hamburger در موبایل
- فونت و برندینگ عمومی
- منوهای native وردپرس

اما قالب نباید منطق رزرو، پرداخت، کیف پول، داشبورد، REST یا دیتابیس را پیاده‌سازی کند.

## 4. نقش درست پلاگین

پلاگین `webtanan-booking` باید مالک این بخش‌ها باشد:

- CPT پزشکان: `saas_doctors`
- جداول عملیاتی `wp_saas_*`
- REST API
- رزرو نوبت
- lock کردن اسلات
- پرداخت
- کیف پول
- داشبورد پزشک
- پنل بیمار
- پروفایل پزشک
- دریافت نوبت
- رسید/فاکتور
- داده‌های لیست پزشکان

اما خروجی HTML پلاگین باید با ساختار sample هماهنگ باشد. یعنی پلاگین نباید کارت، modal، dashboard یا صفحه پزشک را با زبان طراحی جداگانه بسازد.

## 7. برداشت درست از جریان رزرو

جریان رزرو نباید صرفاً یک modal ظاهری باشد. باید پایدار، قابل پرداخت مجدد و قابل رسیدگیری باشد.

جریان مطلوب:

1. کاربر وارد پروفایل پزشک می‌شود.
2. در sidebar فرم رزرو نمونه را می‌بیند.
3. تاریخ را انتخاب می‌کند.
4. اسلات‌ها از REST لود می‌شوند.
5. ساعت را انتخاب می‌کند.
6. پلاگین `POST /appointments/lock` را صدا می‌زند.
7. کاربر وارد صفحه checkout می‌شود.
8. checkout خلاصه نوبت، هزینه، قوانین و روش پرداخت را نمایش می‌دهد.
9. بعد از پرداخت موفق، صفحه receipt/factor نمایش داده می‌شود.

مشکل فعلی که گفتید:

«نمی‌توان نوبت رزرو کرد و خطا می‌زند»

این باید جدا از UI بررسی شود. برای رفع آن باید دقیقاً این موارد smoke-test شوند:

- آیا دکمه رزرو هنوز event درست دارد؟
- آیا `doctor_id` درست به JS می‌رسد؟
- آیا تاریخ شمسی/میلادی درست به REST می‌رود؟
- آیا route مربوط به `appointments/lock` موجود است؟
- آیا nonce در درخواست هست؟
- آیا پاسخ خطای REST در UI خوانا نمایش داده می‌شود؟
- آیا تغییر DOM باعث شده selectorهای JS مثل `[data-webtanan-booking-open]` یا `[data-webtanan-widget="booking-modal"]` پیدا نشوند؟

برداشت من:

قبل از ادامه UI، باید جریان رزرو یک تست انتها به انتها شود و هیچ تغییری در ظاهر نباید selectorهای رزرو را بشکند.

- انگلیسی: `Webtanan Booking`

## 13. چیزی که باید از شما تایید بگیرم

قبل از اجرای فاز اصلاحی، لازم است شما این موارد را تایید یا اصلاح کنید:

1. آیا قالب `webtanan-saas-theme` باید همچنان shell اصلی سایت باشد؟
2. آیا همه صفحات پلاگین باید داخل header/footer قالب نمایش داده شوند؟
3. آیا dashboardها باید حتماً زیر header قالب باشند و full canvas حذف شود؟
4. آیا صفحه checkout باید مستقل باشد و modal فقط برای انتخاب اولیه استفاده شود؟
5. آیا فرم رزرو sidebar در پروفایل پزشک باید دقیقاً مطابق `dr-profile.html` باشد؟
6. آیا sidebar بیمار/پزشک باید از یک map مرکزی در پلاگین ساخته شود؟
7. آیا صفحه لیست پزشکان باید دقیقاً layout `dr-list.html` را داشته باشد؟
8. آیا صفحه اصلی باید دقیقاً از `index.html` بازسازی شود یا فقط نزدیک به آن باشد؟
9. آیا CSSهای قبلی پلاگین اجازه حذف کامل دارند؟
10. آیا برای رزرو، اولویت با رفع engine و checkout است یا با pixel-perfect کردن UI؟

## 14. معیار پذیرش فاز بعدی

فاز بعدی فقط وقتی موفق است که:

- صفحه اصلی شبیه `index.html` باشد.
- صفحه لیست پزشکان شبیه `dr-list.html` باشد.
- صفحه پزشک شبیه `dr-profile.html` باشد.
- داشبورد پزشک شبیه `dr-dashboard.html` باشد.
- پنل بیمار شبیه `patent-dashboard.html` باشد.
- sidebarها پویا و role-aware باشند.
- در موبایل sidebar به hamburger تبدیل شود.
- رزرو نوبت بدون خطا تا lock/checkout/receipt کار کند.
- هیچ route error یا selector error در console نباشد.
- هیچ raw data مثل `lock_token`, `appointment_id`, `Array`, enum خام یا متن developer-facing در UI دیده نشود.

## 15. برداشت نهایی من

برداشت نهایی من این است:

پروژه نباید «پلاگینی با چند قالب پراکنده» باشد. باید یک محصول SaaS یکپارچه باشد که sample HTML زبان طراحی آن است، قالب shell عمومی را می‌دهد، و پلاگین داده و عملیات را داخل همان shell تزریق می‌کند. نقطه شروع اصلاح باید نه CSS، بلکه تعیین source of truth برای هر صفحه و ساخت sidebar پویا باشد. هم‌زمان باید جریان رزرو end-to-end تست و تثبیت شود، چون UI بدون رزرو سالم ارزشی ندارد.
